Chuẩn bị môi trường test

  • Tài khoản: admin / admin123 (quản lý). Tạo thêm tài khoản Quầy & Bếp ở màn Nhân viên để test phân quyền thật.

  • Reset dữ liệu mẫu: npm run db:seed (bỏ qua nếu đã có dữ liệu — xóa data/tram-banh.db* nếu muốn seed lại từ đầu).
Bẫy dev sau khi đổi nhánh / pull: Turbopack có thể giữ cache .next cũ khiến route con API (/api/orders/[id]/chuyen, /xac-nhan-sua) trả 404 → nút nhận làm / xong / hủy bấm không ăn. Xử lý: dừng dev, rm -rf .next, chạy lại npm run dev. Chỉ xảy ra ở dev; bản Docker build sạch không dính.

Đều thực hiện được.
P4Không có bảo vệ route /quanly phía server BIÊN
Đăng nhập Quầy/Bếp rồi gõ thẳng URL /quanly, /quanly/nhan-vien.
Trang mở nhưng rỗng/không dữ liệu vì API trả 403. Bảo vệ nằm ở tầng API, không phải route. (Xem mục Điểm cần lưu ý.)

3

Vòng đời & chuyển trạng thái

F1Luồng đầy đủ NV
Quầy tạo đơn → Bếp Nhận làm → Xong → Quầy Hoàn tất (chọn kiểu kết thúc).
Trạng thái đi đúng thứ tự (4 mốc, không còn da_nhan); Nhật ký ghi đủ các mốc kèm người thực hiện & thời điểm.
F2Hoàn tất thiếu kiểu kết thúc BIÊN
Gọi chuyển sang hoan_tat mà không kèm ketThucKieu (qua API).
409 — “Chọn hình thức kết thúc (giao khách / đã ship)”. Trên UI luôn phải chọn 1 trong 2.
F2blen_tu bị chặn ở server BIÊN
Gọi API chuyển sang hoan_tat với ketThucKieu: "len_tu".
409 — “Hình thức kết thúc không hợp lệ (chỉ giao khách / đã ship)”. Chỉ nhận giao_khach và da_ship; đơn cũ đã lưu len_tu vẫn đọc/thống kê bình thường.
F3Hủy thiếu lý do BIÊN
Bấm Hủy đơn nhưng để trống lý do (hoặc gọi API không lyDoHuy).
UI không chuyển; API 409 — “Nhập lý do hủy”.
F4Hủy đơn đã hoàn tất BIÊN
Với đơn hoan_tat, thử hủy.
Không có nút Hủy; API từ chối (điều kiện from ≠ hoan_tat, huy).
F5Chống race — 2 người bấm cùng lúc BIÊN
Mở cùng một đơn moi trên 2 máy, cùng bấm Nhận làm gần như đồng thời (hoặc gửi 2 request chuyen liên tiếp).
Chỉ 1 thành công. Người sau nhận “Đơn vừa được người khác xử lý, hãy tải lại” (UPDATE có điều kiện trangThai = from, changes === 0).
F6Hoàn tác chỉ trước khi đơn hoàn tất NV
Bếp: banh_xong → dang_lam và dang_lam → moi. Sau khi Quầy đã bấm hoan_tat thì thử lại.
Trước khi hoàn tất thì hoàn tác được; đơn hoan_tat không còn bước lùi nào.
F7Reset cờ ĐÃ SỬA khi tiến bước KT
Đơn có daSua=1, chuyển sang hoan_tat.
daSua tự về 0 (nhãn ĐÃ SỬA biến mất).
F8Đơn cũ kẹt ở da_nhan vẫn kết thúc được KT
Đặt tay một đơn về da_nhan trong DB (update orders set trang_thai='da_nhan' where id=?), mở bảng đơn Quầy rồi bấm Hoàn tất.
Cột Quầy đã nhận tự hiện lại (kanban thành 4 cột) khi còn đơn như vậy, bấm ✅ Hoàn tất chạy bình thường, xong thì cột tự biến mất (về 3 cột).

Giá, phụ thu & tổng tiền

Nguồn: src/lib/money.ts, orders-service.ts (apGiaMon). Giá món = base + phụ thu (Cốt/Mứt/Topping). Tổng = Σ món + Σ phụ kiện + phí ship.

M1Phụ thu % NV
Cốt phụ thu 10%, base 200.000đ.
Phụ thu = 20.000đ (10% × 200k, làm tròn 1.000đ). Giá cuối 220.000đ.
M2Phụ thu tiền cố định + làm tròn % KT
Mứt +5.000đ (tiền). Cốt 7% trên base 205.000đ (=14.350 → làm tròn).
Tiền cố định cộng nguyên. % làm tròn về bội số 1.000đ (14.350 → 14.000).
M3Size không phụ thu KT
Kiểm tra menu ⋮ của Size ở màn Sản phẩm.
Size chỉ có Đổi tên/Xóa, không có mục phụ thu; đổi Size không đổi giá.
M3bDanh mục Kem — như Cốt KT
Kem là vị mới (loai kem trong banh_options, cột order_items.kem). Có sẵn “Kem mặc định” (miễn phí). Đặt phụ thu %/tiền cho một vị kem, tạo đơn chọn vị đó.
Phụ thu kem cộng đúng vào giá (server tính qua phanTichGiaMon, thứ tự breakdown: cốt → kem → mứt → topping). Chọn kem là tùy chọn (có nút “Không”), không chặn tạo đơn. Đơn cũ (kem null) không ảnh hưởng.
M4Giá tính lại ở server BIÊN
Gửi API tạo đơn với giaBase hợp lệ nhưng gia sai (thấp/cao bất thường).
Server bỏ qua gia client gửi, tính lại theo giaBase + phụ thu hiện hành (apGiaMon). Tổng lưu đúng.
M5Ghi đè tổng tiền (giảm giá) NV
Tick “Cho phép sửa giá thủ công”, nhập tổng < tổng tính.
Đơn lưu theo tongTienGhiDe; Còn lại = tổng ghi đè − cọc.
M6Tiền cọc bắt buộc > 0 BIÊN
Để cọc = 0 hoặc trống.
UI chặn (nút mờ, nhắc “Vui lòng nhập tiền khách đã cọc”); API: “Vui lòng nhập tiền khách đã cọc (lớn hơn 0)”.
M7SĐT khách phải là di động VN 10 số BIÊN
Nhập SĐT sai định dạng (vd 8 số, đầu số lạ).
UI báo “Số điện thoại không hợp lệ (di động VN)”; API: “Số điện thoại khách không hợp lệ (số di động VN 10 chữ số)”. SĐT người nhận ship nếu nhập cũng phải hợp lệ.

Quản lý: vị / phụ kiện / nhân viên

Q1Xóa vị / phụ kiện không ảnh hưởng đơn cũ KT
Tạo đơn dùng một vị + phụ kiện. Sau đó xóa vị/phụ kiện đó ở màn Sản phẩm. Mở lại đơn cũ.
Đơn cũ vẫn hiển thị đúng vị/phụ kiện (lưu snapshot tên+giá, không tham chiếu id).
Q2Không tự xóa tài khoản đang đăng nhập BIÊN
Admin thử xóa chính mình.
Nút Xóa không hiện với chính mình; API: “Không thể tự xóa tài khoản đang đăng nhập” (400).
Q3Không xóa admin gốc BIÊN
Thử xóa tài khoản admin.
API: “Không thể xóa tài khoản admin gốc” (400).
Q4Không xóa NV đã có lịch sử đơn BIÊN
Xóa một nhân viên đã tạo/làm/giao đơn.
409 — “Nhân viên đã có lịch sử đơn hàng, không thể xóa — hãy khóa tài khoản thay thế”.
Q5Trùng tên đăng nhập BIÊN
Tạo 2 tài khoản cùng username.
409 — “Tên đăng nhập đã tồn tại”.
Q6Khóa tài khoản / đổi vai trò có hiệu lực ngay KT
Đổi vai trò một NV đang đăng nhập ở máy khác; hoặc set active=0 (hiện chỉ qua API/DB — UI chưa có nút khóa).
Lần thao tác kế tiếp của NV đó áp quyền mới ngay; nếu active≠1 → coi như chưa đăng nhập (401), không chờ hết hạn token.

Test nhanh bằng curl

Dùng để kiểm tra API và tái hiện case biên mà không cần bấm tay. Chạy trên máy đang chạy dev (cổng 3000).

# 1) Đăng nhập, lưu cookie phiên
curl -s -c cj.txt -X POST http://localhost:3000/api/login \
  -H "content-type: application/json" \
  -d '{"username":"admin","password":"admin123"}'

# 2) Danh sách đơn hôm nay
curl -s -b cj.txt "http://localhost:3000/api/orders?trangThai=moi,dang_lam,banh_xong,da_nhan"

# 3) Chuyển trạng thái (nhận làm đơn id=4)
curl -s -b cj.txt -X POST http://localhost:3000/api/orders/4/chuyen \
  -H "content-type: application/json" -d '{"to":"dang_lam"}'

# 4) Hoàn tất — bắt buộc ketThucKieu (thiếu sẽ 409)
curl -s -b cj.txt -X POST http://localhost:3000/api/orders/4/chuyen \
  -H "content-type: application/json" \
  -d '{"to":"hoan_tat","ketThucKieu":"giao_khach"}'

# 5) Hủy — bắt buộc lyDoHuy
curl -s -b cj.txt -X POST http://localhost:3000/api/orders/4/chuyen \
  -H "content-type: application/json" \
  -d '{"to":"huy","lyDoHuy":"khách đổi ý"}'
Giá trị hợp lệ: to ∈ moi/dang_lam/banh_xong/hoan_tat/huy (da_nhan không nhận nữa) · ketThucKieu ∈ giao_khach/da_ship (len_tu bị chặn) · nguon ∈ tai_quay/zalo/messenger/dien_thoai/khac · hinhThucNhan ∈ tai_tiem/ship · kieuPhiShip ∈ freeship/theo_app.

Điểm cần lưu ý (đã biết)

  • Route /quanly không chặn phía server — bảo vệ dựa vào API trả 403. Người không phải quản lý mở trang sẽ thấy trang rỗng chứ không bị chặn URL. Cân nhắc thêm kiểm tra vai trò ở tầng trang nếu cần chặt hơn.
  • Khóa tài khoản chưa có nút trên UI — schema/API hỗ trợ active, nhưng màn Nhân viên chỉ có Sửa tên / Đổi mật khẩu / Xóa. Thông báo lỗi xóa lại gợi ý “hãy khóa tài khoản” → nên bổ sung nút khóa/mở.
  • API /api/products chưa gắn UI — bánh mẫu là 1 sản phẩm cố định (“Bánh kem sinh nhật theo mẫu”); màn Sản phẩm chỉ cấu hình vị + phụ kiện.
  • Phí ship chỉ 2 lựa chọn, đều = 0đ — Freeship / Theo app ship, không nhập số. Đơn cũ có thể còn phiShip > 0 (hiện dòng cảnh báo khi sửa).
  • Mật khẩu admin mặc định công khai (admin/admin123, có in trong HDSD) — đổi ngay sau khi deploy thật.
  • Quick tunnel cloudflared là tạm — URL đổi mỗi lần khởi động lại, không cam kết uptime; deploy thật dùng Docker + named tunnel/domain.
